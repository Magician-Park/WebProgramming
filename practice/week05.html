CSS 01 / STRUCTURE & STYLE

내용과 디자인을 분리하기

Lec04 강의자료 2~6쪽

HTML은 제목·문단·링크 같은 콘텐츠의 구조와 의미를 표현한다. CSS(Cascading Style Sheets)는 색상·글꼴·크기·간격·배치 같은 외형을 지정한다. 공통 규칙을 한곳에 모으면 여러 요소와 페이지의 디자인을 일관되게 바꿀 수 있다.

CSS1은 1996년, CSS2는 1998년에 등장했고 이후 CSS는 여러 모듈로 발전했다. ‘CSS3’라는 이름을 하나의 고정된 기능 묶음이나 모든 브라우저의 완전한 지원으로 이해하지 않고, 사용하는 기능과 환경을 함께 확인한다.

선택자 {
  속성: 값;
  속성: 값;
}

h3 {
  color: #346248;
  font-style: italic;
}
  • 선택자는 스타일을 적용할 대상을 고른다.
  • 선언은 속성 이름과 값을 콜론으로 연결하고 세미콜론으로 구분한다.
  • 중괄호 안에 여러 선언을 작성하면 같은 요소에 여러 속성을 적용할 수 있다.
  • 다른 속성의 선언이 모이는 것과 같은 속성의 충돌은 구분한다. 같은 속성이 충돌할 때는 단순히 무조건 마지막 줄이 이긴다고 판단하지 않는다.

GIT 01 / THE BIG PICTURE

Git과 GitHub, 네 단계의 흐름

Git은 내 컴퓨터에서 코드의 변경 이력을 관리하는 도구다. GitHub는 원격 저장소를 호스팅하고 협업 기능을 제공하는 서비스다. 파일을 저장하는 것, 커밋하는 것, GitHub에 반영하는 것은 서로 다른 단계다.

  1. 1. 작업 폴더

    HTML·CSS 파일을 수정하고 저장

  2. 2. 스테이징

    git add로 다음 기록에 넣을 변경 선택

  3. 3. 로컬 커밋

    git commit으로 변경의 스냅샷 기록

  4. 4. 원격 저장소

    git push로 커밋과 브랜치를 GitHub에 반영

add·commit·push를 혼동하지 않기

add만 하면 커밋이 만들어지지 않는다. commit만 하면 원격에 반영되지 않는다. push는 현재 폴더의 모든 미커밋 변경을 올리는 것이 아니라 기록된 커밋을 전송한다.

브랜치는 작업 이력의 흐름을 가리키는 이름이고, origin은 원격 저장소에 붙인 별칭이다. origin이 GitHub 계정 이름이거나 main이 모든 저장소의 필수 이름인 것은 아니다.

개념 확인: GitHub Docs · About Git

GIT 02 / ONE-TIME SETUP

작업 전 초기 설정

명령은 터미널에서 사용한다. 먼저 Git 설치 여부를 확인하고 커밋 작성자 정보를 설정한다. 아래 이름과 이메일 값은 자리표시자이며 실제 계정에 사용할 값으로 바꾼다.

git --version

git config --global user.name "PUBLIC_ACTIVITY_NAME"
git config --global user.email "GITHUB_NOREPLY_EMAIL"

git config --get user.name
git config --get user.email
설정의 역할과 범위
항목의미
user.name커밋에 기록할 작성자 이름. GitHub 로그인용 ID 설정과는 다르다.
user.email커밋 작성자 메타데이터. 계정의 이메일 설정에서 확인한 GitHub noreply 주소를 사용할 수 있다.
--global이 컴퓨터의 사용자 계정에서 사용하는 저장소들에 적용하는 기본값.
--local현재 Git 저장소에만 적용하며 global 설정보다 우선한다. 저장소 준비 후 사용할 수 있다.

커밋 작성자 정보는 GitHub 인증 정보를 대신하지 않는다. 이름을 설정했다고 자동으로 로그인되는 것은 아니다. 개인정보 공개를 줄이려면 실명 대신 공개 활동명을 사용하고, noreply 값은 계정 설정의 실제 주소를 확인해 입력한다. 이 페이지에는 실제 이메일이나 인증 값을 기록하지 않는다.

설정 확인: Git 초기 설정 · GitHub 커밋 이메일 설정 · Git 설치 안내

GIT 03 / INIT OR CLONE

새 프로젝트와 기존 저장소를 구분하기

A. 내 폴더에서 새로 시작

Git으로 관리하지 않던 프로젝트 폴더에 들어가 저장소를 만든다. -b main은 이 예제의 최초 브랜치 이름을 main으로 지정한다.

cd "/path/to/project"
git init -b main
git status

B. GitHub에 기존 코드가 있음

기존 원격의 파일과 이력을 clone으로 가져와 작업한다. GITHUB_ID와 REPOSITORY를 실제 저장소 값으로 바꾼다.

git clone https://github.com/GITHUB_ID/REPOSITORY.git
cd REPOSITORY
git status
git remote -v

A와 B는 시작 상황에 따른 선택지다. 이미 clone한 폴더에 다시 새 저장소를 만드는 과정을 반복하지 않는다. .git 디렉터리는 Git의 관리 정보를 담으며, 페이지의 콘텐츠 폴더와 구분한다. init -b는 Git 2.28 이상을 기준으로 한다.

이미 GitHub에 README나 커밋이 있는 저장소라면 B가 자연스러운 시작이다. A에서 새 로컬 이력을 만들었다면 첫 push의 대상은 별도 초기 커밋이 없는 빈 원격 저장소로 준비한다.

시작 방법: git init · GitHub에 로컬 코드 추가

GIT 04 / REVIEW, ADD & COMMIT

변경을 확인하고 한 묶음으로 기록하기

프로젝트 파일을 저장한 뒤 먼저 상태와 차이를 확인한다. 이번 커밋에 포함할 파일을 고르고, 스테이징된 내용도 다시 확인한 다음 커밋한다.

git status

git diff

git add index.html style.css practice/week05.html practice/practice.css

git diff --staged

git commit -m "5주차 CSS와 Git 학습 기록 추가"

git log --oneline -5
git status

명령의 파일 이름은 웹페이지 프로젝트의 예시다. 실제로 수정한 파일 이름을 사용하며, 새로 추가한 이미지·스크립트·문서가 있다면 함께 검토한다. git diff는 일반적으로 추적 중인 파일의 미스테이징 차이를 보여 주며 새 파일은 status와 파일 내용으로 확인한다.

각 명령에서 확인하는 범위
명령하는 일확인할 점
git status현재 파일과 스테이징 상태 확인누락된 새 파일과 의도하지 않은 변경을 찾는다.
git diff작업 폴더와 스테이징 사이의 차이 확인수정한 코드가 의도한 변경인지 읽는다.
git add FILE그 시점의 파일 내용을 스테이징커밋에 넣을 변경을 선택한다.
git diff --staged다음 커밋에 들어갈 변경 확인저장하려는 내용이 실제로 준비됐는지 읽는다.
git commit -m스테이징을 로컬 이력으로 기록무엇을 바꿨는지 알 수 있는 메시지를 남긴다.
git log --oneline최근 커밋의 요약 확인새 기록이 생성됐는지 확인한다.

add 뒤에 또 수정했다면 다시 확인

스테이징은 자동으로 최신 파일 내용에 맞춰 바뀌지 않는다. add 후 파일을 더 수정했다면 git diff와 git diff --staged를 비교하고 필요한 내용을 다시 add한다. 커밋에는 작업 폴더의 모든 변경이 아니라 준비된 내용이 들어간다.

커밋은 한 가지 목적을 설명할 수 있는 단위로 묶는다. 예를 들어 ‘CSS 선택자 예제 추가’, ‘잘못된 내부 링크 수정’처럼 바뀐 행동이나 내용을 메시지로 표현한다.

변경 기록 확인: Git · Recording Changes

# .gitignore 예시

git status --short를 읽는 예

git restore --staged style.css
git status

GIT 06 / FIRST PUSH TO GITHUB

원격 연결과 첫 업로드

새 로컬 저장소의 첫 커밋을 만들었다면 GitHub에 업로드할 원격 저장소를 준비한다. 다음은 A 방식으로 시작한 프로젝트와 빈 원격 저장소를 연결하는 예시다.

  1. GitHub에서 새 Repository를 만들고 공개·비공개 범위를 선택한다.
  2. 새 로컬 이력을 올릴 빈 저장소라면 GitHub 쪽 README·라이선스·gitignore 초기 생성은 생략한다.
  3. 저장소 화면의 원격 URL을 복사한다.
  4. 로컬 프로젝트에서 origin을 연결하고 주소를 확인한다.
  5. 올바른 계정과 권한으로 인증한 뒤 첫 push를 한다.
git remote add origin https://github.com/GITHUB_ID/REPOSITORY.git
git remote -v

git branch --show-current

git push -u origin main

위 명령은 이 예제의 브랜치가 main일 때 사용한다. 실제 브랜치 이름은 확인한 값에 맞춘다. -u는 로컬 브랜치가 추적할 원격 브랜치를 설정하므로 이후 같은 브랜치에서는 git push나 git pull을 더 간단히 사용할 수 있다.

작성자 설정과 인증은 별도

HTTPS 방식에서는 GitHub CLI나 Git Credential Manager 등의 로그인 흐름, 또는 토큰 기반 인증을 사용할 수 있다. SSH 방식은 GitHub에 등록한 SSH 키로 인증한다. HTTPS Git 작업에 GitHub 계정의 일반 비밀번호를 사용하는 방식과 구분한다.

clone한 저장소는 origin이 이미 연결되어 있을 수 있다. 같은 별칭을 다시 추가하기 전에 git remote -v를 읽고 대상이 맞는지 확인한다. 토큰·개인 키를 URL이나 소스에 넣지 않는다.

첫 업로드: GitHub 로컬 코드 추가 · git push · GitHub 인증

GIT 07 / EVERYDAY WORKFLOW

다음 수정부터 반복하는 순서

원격과 추적 브랜치가 설정된 뒤에는 init이나 remote add를 매번 반복하지 않는다. 작업 전 상태와 원격 변경을 확인하고, 수정·기록·전송의 순서를 반복한다.

# 1. 작업 전: 커밋하지 않은 변경이 없는지 확인
git status

# 2. 다른 컴퓨터·GitHub에서 바뀐 내용이 있다면 가져오기
git pull --ff-only

# 3. HTML/CSS를 수정하고 브라우저에서 확인한 뒤
git diff
git add index.html style.css practice/week05.html practice/practice.css
git diff --staged
git commit -m "CSS 선택자 설명과 출력 예제 보완"

# 4. 원격으로 전송
git push

# 5. 상태와 기록 확인
git status
git log --oneline -5

pull은 원격 변경을 가져와 현재 브랜치에 반영하는 과정이다. --ff-only는 이력을 단순히 앞으로 이동할 수 있는 경우만 허용한다. 로컬과 원격이 각각 다른 커밋으로 갈라지면 중단하므로 이 옵션이 모든 충돌을 자동 해결하는 것은 아니다.

작업 폴더에 수정이 남아 있다면 먼저 어떻게 보관할지 결정한다. 원격 변경과 같은 부분을 동시에 수정했다면 두 변경을 읽고 병합·재배치 등으로 정리해야 한다. 오류를 없애기 위해 원격 이력을 강제로 덮어쓰는 방식으로 처리하지 않는다.

GitHub 화면에서 마지막 확인

  • 대상 Repository와 브랜치가 올바른지 확인한다.
  • 방금 만든 커밋 메시지와 수정 파일이 보이는지 확인한다.
  • GitHub 파일 내용에 수정한 HTML·CSS가 반영됐는지 읽는다.
  • push와 웹사이트 배포를 구분한다. 코드를 올렸다고 자동으로 공개 웹페이지가 생기는 것은 아니다.

동기화 기준: git pull

메시지를 읽고 원인부터 확인하기

대표적인 상태·오류와 다음 확인
메시지 또는 상황가능한 원인먼저 확인할 것
not a git repository프로젝트의 Git 저장소 밖에서 명령을 실행함현재 폴더와 .git 위치 확인. 기존 저장소라면 init을 반복하기보다 올바른 폴더로 이동.
Author identity unknown커밋 작성자 정보가 설정되지 않음user.name·user.email의 global 또는 local 값 확인.
nothing to commit새 변경이 없거나 커밋할 내용이 준비되지 않음파일 저장 여부와 git status를 읽고 실제 상태 확인.
remote origin already existsorigin이 이미 등록되어 있음git remote -v로 대상 확인. URL 변경이 필요할 때만 set-url 사용.

non-fast-forward / ff-only 중단원격에 로컬에 없는 커밋이 있거나 이력이 갈라짐fetch 후 로컬·원격 기록을 비교하고 통합 방법 결정.
Authentication failed / 권한 거절인증 방식·계정·저장소 권한이 맞지 않음원격 URL, 로그인 계정과 쓰기 권한 확인. 작성자 설정만으로 해결되지 않음.
# 원격 주소를 읽고 필요할 때만 수정
git remote -v
git remote set-url origin https://github.com/GITHUB_ID/REPOSITORY.git

# 원격 기록을 가져와 비교: 작업 파일을 바로 합치지 않음
git fetch origin
git log --oneline --graph --decorate --all

에러 표는 가능한 원인을 정리한 복습 자료다. 메시지 하나만 보고 파일을 삭제하거나 이력을 되돌리지 않고, 현재 저장소·브랜치·파일 상태를 먼저 읽는다. 충돌이 생기면 겹친 부분을 확인해 원하는 내용으로 정리한 뒤 필요한 변경을 다시 기록한다.

    REVIEW / CSS & GIT

    복습 질문

    .term과 #intro는 무엇이 다른가?

    여러 요소에 재사용할 수 있는 class와 한 문서에서 고유한 id를 선택한다.

    :hover와 ::before는 같은 종류인가?

    :hover는 요소의 상태를 고르는 가상클래스, ::before는 생성되는 표현 영역인 가상요소다.

    git add 뒤 파일을 다시 수정하면 커밋에도 바로 포함되는가?

    자동 포함되지 않는다. add한 시점의 내용과 추가 수정이 달라지므로 diff와 staged diff를 확인하고 필요한 내용을 다시 add한다.

    git commit만 하면 GitHub에 파일이 올라가는가?

    로컬 저장소에 기록된다. 원격 반영에는 별도의 push와 올바른 인증·권한이 필요하다.

    기존 저장소를 clone한 뒤 remote add를 매번 하는가?

    clone 과정에서 원격이 설정되어 있을 수 있다. remote -v로 확인하며 초기화를 매 작업마다 반복하지 않는다.

    user.name 설정은 GitHub 로그인인가?

    커밋 작성자 메타데이터다. GitHub 인증과는 별도다.

    git pull --ff-only가 거절되면 모든 파일이 사라지는가?

    이력을 단순하게 이동할 수 없으면 작업을 중단한다. 상태와 이력을 읽고 원격·로컬 변경을 통합할 방법을 결정한다.

    push를 하면 웹사이트도 자동 배포되는가?

    원격 저장소의 커밋이 갱신되는 것이다. 실제 사이트 배포는 사용하는 호스팅의 별도 절차를 따른다.
